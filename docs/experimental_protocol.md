# Iota Lab Experimental Protocol

## Core Rule

After the baseline experiment, exactly one controlled parameter changes per experiment.

## Controlled Parameters

A controlled parameter is any flattened user-configured input recorded in the experiment snapshot, except operational metadata ignored by the lab runner:

- `experiment.id`
- `experiment.objective`
- `lab.database`
- `lab.experiments_dir`
- `run.output_dir`
- `simulation_version`

Derived quantities, expanded defaults, runtime metrics, artifact paths generated by the runner, and post hoc analysis outputs are not controlled parameters. The one-parameter guard should compare consumed configuration inputs, not downstream derived values, so one human intervention is not rejected merely because it changes multiple derived fields.

## Baseline

The first experiment in a new database establishes the baseline. It has no previous run to compare against, so it records no parameter diff.

## Rejection Conditions

The runner refuses to start an experiment after the baseline when:

- zero controlled parameters changed
- more than one controlled parameter changed

This keeps each run interpretable as a single intervention against the previous experiment.

## Lineage and Branching

The current lab history is chronological: each guarded run is compared to the previous experiment. That is sufficient for linear sweeps, but it is awkward for parallel branches from a shared baseline.

Future runner support should add an optional `experiment.parent_id`. When present, the one-parameter guard should compare the current run against the declared parent rather than the immediately previous experiment. That turns experiment history into a directed acyclic graph while preserving single-intervention discipline.

## Versioning

Every experiment records `simulation_version`. A version change is a lineage boundary: it should force a new baseline, require `--force`, or require an explicit golden-equivalence gate before the run is interpreted as part of a controlled sweep.

## Measurement-Only Analyses

Post hoc analysis scripts that consume saved states, replay existing configurations, or launch resampled continuations without registering a new lab experiment are measurement-only artifacts. They may vary analysis settings such as checkpoint cadence, continuation horizon, sample count, and component connectivity without violating the one-parameter experiment guard, but their outputs must be labeled as analysis artifacts rather than new controlled experiments.

`src/openness_timeline.py` is in this category. It measures the outcome entropy of resampled futures from scheduled checkpoints; it does not change the simulation law.

## Model-Class Boundaries

Hard conservation, deactivation, reversibility, recharge, or fossil-state retention are model-class changes. They require a new `simulation_version`, a fresh baseline or explicit parent, and golden replay checks before comparison with v0.1 results.

## Artifact Retention

The database stores artifact metadata, not PNG bytes. Snapshot PNGs are retained according to the active `artifacts` configuration, while metrics remain in SQLite for every tick.

Default retention keeps the initial snapshot, final snapshot, every fourth intermediate snapshot, run plots, comparison plots, and CSV metrics.
